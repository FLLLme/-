纯静态博客接上可视化后台，一天之内踩了六个坑。其中五个我判断错了方向——这份复盘记录了每个坑的真实根因，以及为什么"先观测再改代码"比想象中重要得多。---

## 结果先行

一天之内，这个博客从"一堆静态文件"变成了可以这样写文章：

打开 `https://flllme.github.io/-/admin/` → 用 GitHub 登录 → 写标题、选日期、加标签、写正文 → 保存 → 一分钟内上线。

技术上没有任何构建流程、没有数据库、没有框架。文章是 Markdown 文件，评论用 Twikoo，AI 问答调 DeepSeek。整套东西靠一个 GitHub Actions 工作流串起来。

但打通这条链路的过程并不顺利。下面六个坑，每一个都真实发生过，而且**其中五个我一开始判断错了方向**。真正值钱的部分在后面。

## 六个坑

### 坑一：Jekyll 悄悄吃掉了所有文章

**现象**：线上 `posts/hello-blog.md` 返回 404，但 `posts/hello-blog.html` 返回 200。

**根因**：GitHub Pages 默认启用 Jekyll。文章以 `---` 包裹的 front matter 开头，Jekyll 把它识别成**自己的**页面元数据，于是把 `.md` 编译成 `.html`，原始文件不再发布。

最能说明问题的是对照组：`README.md` 没有 front matter，被原样保留了。

**修法**：仓库根目录放一个空的 `.nojekyll` 文件，关闭 Jekyll。

这个坑的危险之处在于它**不报错**——站点看起来正常，因为前端会退回到离线数据包，只是内容从此定格在某个快照上。

### 坑三：三个 CDN 全部不可达

**现象**：换了三个 CDN，脚本都加载不下来。

**根因**：`unpkg.com`、`cdn.jsdelivr.net`、`registry.npmmirror.com` 在目标网络环境下均不可靠。而这个 CMS 的单文件包有 **5 MB**，一旦请求挂起（既不返回也不报错），页面就永远停在加载态。

**修法**：把包下载到仓库里，改用相对路径引用，CDN 只作为兜底。同时给每个来源加超时——**CDN 出问题时经常只是长时间挂起，仅靠 `onerror` 会永远等下去**。

### 坑六：上传落错目录，覆盖了博客首页

**现象**："返回主页"显示的是后台登录页。

**根因**：用 GitHub 网页端上传文件时没先点进子目录，文件直接落到了仓库根目录，并且**静默覆盖**了同名的 `index.html`——博客首页被后台页面顶掉了。

**修法**：逐文件确认目标目录。更省事的办法是用 git 推，路径不会错。

### 二、"同一份数据两种结果"是最有价值的线索

坑五之所以能定位，靠的是一个反常现象：**同一个文件，列表能读出标题，编辑器读不出来。**

正常思维会把这两个现象归到同一个原因上，但恰恰是它们的**不一致**指出了方向——既然数据本身没问题，那差异必然在两条代码路径上。

遇到"部分正常、部分异常"，第一步应该是**找出两条路径的分界点**，而不是去检查共用的那份数据。

### 三、静态托管的隐式行为比想象中多

纯静态托管看起来简单，实际上有几个不显眼的默认行为：

* **Jekyll 默认开启**

  ，会处理带 front matter 的 Markdown。
* **路径是大小写敏感的**

  （本地 Windows 不敏感，容易漏测）。
* **MIME 类型由扩展名决定**

  ，

  `.yml`

   会被当成 

  `application/octet-stream`

  。
* **子路径部署**

  （

  `/<repo>/`

  ）下，绝对路径 

  `/api/xxx`

   会指到用户站根目录，相对路径才安全。

**结论：静态站点里，凡是靠约定推断出来的东西，都要显式验证一次。**

## 最后的架构

绕完这些坑，现在的工作流是这样的：

前端始终只读 `posts/`，工作流负责在每次推送时把 `content/posts/` 镜像过去并重建清单。

**为什么要多这一层**：纯静态站点没有后端，浏览器无法枚举服务器上的目录，前端必须靠一份 `manifest.json` 才知道"有哪些文章"。而后台 CMS 只能写内容文件，不会维护这份清单——所以需要一次 CI 把缺口补上。

顺带一提，脚本里有一道安全阀值得保留：**源目录为空时直接中止并报错**。没有它的话，一次路径写错就会把线上文章全部清掉。

## 一句话总结

这六个坑里，真正难的不是任何一个技术点，而是**在信息不足时忍住不去猜**。

下次遇到"功能看似正常、细节全崩"的问题，我的第一步会是：打开控制台，把真实请求打出来。
