## 为什么值得较真

Markdown 的语法十分钟就能学完，这给人一种"它很简单"的错觉。但语法简单和写得好是两件事——就像中文语法不难，写好中文依然很难。

以下十条实践，每一条都对应我在真实写作中踩过的坑。

## 1. 一行一句话，不要硬换行

```markdown
<!-- 不推荐 -->
这是第一句话，这里手动换行了
这是第二句话。

<!-- 推荐 -->
这是第一句话，这里不换行，编辑器的软换行会自动处理。这是第二句话。
```

硬换行在渲染时会变成同一个段落，但在 Git diff 里会产生大量噪声。更重要的是，当你中途插入一句话时，硬换行的文本需要重新调整整段的对齐。

## 2. 标题层级严格递进

不要为了字号而用 `####`。标题反映的是**内容的语义层级**，不是视觉大小。如果觉得 `##` 太大，应该改 CSS，而不是降级标签。

自动生成的目录（TOC）直接依赖层级结构。一个 `##` 下面直接跟 `####`，生成的目录会出现无法折叠的空洞。

## 3. 代码块永远标注语言

````markdown
```python
def hello(): ...
```
````

标注语言后，语法高亮、复制按钮的语言提示、某些静态站点的构建期校验都能正常工作。不标注等于放弃了这些能力。

代码块内的缩进用空格，不要用 Tab。不同编辑器对 Tab 宽度的解释不一致，混用会导致对齐错乱。

## 4. 列表和它前后的段落之间留空行

```markdown
这是段落。
1. 第一项
2. 第二项
```

很多解析器（尤其是 CommonMark 实现）会把紧贴段落的列表识别为段落的一部分。留一个空行，成本为零，兼容性收益很大。

## 5. 用引用块表达"注意"

```markdown
> **注意**：该接口在 2026 年 6 月后不再返回 `usage` 字段。
```

引用块是 Markdown 里唯一一个"独立于正文语气"的容器。用它承载警告、前提条件、历史背景，读者的视线会自然地停在上面。

## 6. 表格只用于可比较的数据

Markdown 表格的语法很笨重，且不能换行、不能合并单元格。判断标准很简单：

- **能列成"同一组属性 × 多个对象"** → 用表格。
- **是流程、是论述、是示例** → 用列表或小标题。

## 7. 链接使用语义化的锚文本

```markdown
<!-- 不推荐 -->
详见 [这里](https://example.com/docs)。

<!-- 推荐 -->
详见 [DeepSeek API 官方文档](https://example.com/docs)。
```

原因有三：屏幕阅读器会朗读锚文本；搜索引擎以此判断链接主题；读者在快速扫读时，语义化的链接本身就是有效信息。

## 8. 图片要有替代文本

```markdown
![流式请求的时间线示意图](./assets/stream-timeline.png)
```

替代文本在图片加载失败、网络受限、无障碍阅读三种场景下都会生效。这三件事在中文技术内容里都很常见。

## 9. Frontmatter 只放"机器要读"的东西

```yaml
---
title: Markdown 写作的十条工程实践
date: 2026-09-18
tags: [写作, Markdown]
excerpt: 一句话摘要，会被列表页和 SEO 直接消费。
---
```

好的 Frontmatter 判断标准：**这里的每一个字段，都有代码在读取它**。如果 `mood: 平静` 这种字段没有任何程序消费，它就应该写在正文里，而不是元数据里。

## 10. 摘要写"结论"，不写"概述"

对比一下：

- ❌ "本文介绍了 Markdown 写作的一些技巧。"
- ✅ "Markdown 的语法只有一页纸，但写好很难。这十条实践来自三年间近 400 篇技术笔记的复盘。"

第一句是目录，读者看完仍然不知道要不要读。第二句给出了**信息密度**和**可信度来源**，它本身就是一个可以独立存在的结论。

## 一点补充：建立自己的片段库

写作效率的最大瓶颈不在打字速度，而在"我知道这里该放一个表格，但我不想每次都手写语法"。

建议维护一个个人片段库（VS Code 的 user snippets、Obsidian 的模板插件都可以），把最常用的五个结构固化下来：**对比表格**、**带语言的代码块**、**注意引用块**、**步骤列表**、**文章 Frontmatter**。

写作者的时间应该花在**想清楚**上，而不是花在**敲符号**上。
